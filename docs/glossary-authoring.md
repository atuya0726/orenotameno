# 用語学習の編集方針

用語学習では、選んだ1つの単語・概念を自分の言葉で説明する。関連語まで一度に覚えさせるために、1項目へ詰め込まない。この方針は収録済みの用語の修正、新規追加、AIが作る評価項目に適用する。

評価項目は「基本」と任意の「深掘り」に分ける。基本を満たせば合格とし、深掘りは追加の達成として扱う。範囲と区分の判断には[用語評価の基準](glossary-rubric.md)を使う。

## 原則は1用語につき1概念

- 意味や用途が異なり、単独で説明できる語は別の用語にする。一緒に出題されることや、比較すると分かりやすいことは、まとめる理由にしない。
- サーバー証明書とクライアント証明書、クラッシングとファストトラッキング、IDSとIPS、RTOとRPOなどはそれぞれ分ける。
- 関連する語は `related` でつなぐ。説明例で関連語に触れることはできるが、相手の語の定義まで答えることを必須にしない。
- 「1単語」は文字列の短さではなく、説明対象が1つであることを指す。`PKI（公開鍵基盤）` のような略称と正式名は同じ用語として扱う。
- ACID特性のように複数の要素から成る概念は、その概念を説明するための要素を扱える。一方、個別の手法や指標を選んだときに、同じ分類に属する別の手法や指標の説明まで求めない。
- 総称・分類の項目では、何をまとめた概念かを中心に問う。関連する性質や構成要素それぞれの詳しい定義まで一括で要求しない。例えば「情報セキュリティの3要素」は機密性・完全性・可用性を挙げればよく、真正性・信頼性・責任追跡性・否認防止の説明はそれぞれの用語で扱う。これらも情報セキュリティに関係する性質だが、基本の3要素とは学習項目の範囲を分ける。

| 選んだ用語 | 説明してほしい中心的な内容 | 別の用語に分ける内容 |
|---|---|---|
| クラッシング | 資源を追加してクリティカルパス上の作業期間を短縮する | ファストトラッキングの方法 |
| ファストトラッキング | 通常は順番に行う作業を並行させて期間を短縮する | クラッシングの方法 |
| サーバー証明書 | 接続先のサーバーを認証する証明書 | クライアント・コードサイニング・EV証明書それぞれの定義 |
| RTO | 中断から復旧までの目標時間 | RPO・RLOの定義 |
| 情報セキュリティの3要素 | 機密性・完全性・可用性という3要素の総称 | 個々の性質の詳しい定義、真正性などの追加の性質 |

## 別名と関連語を区別する

`aliases` は同じ概念の表記ゆれ・略称・正式名に使う。`サーバ証明書` → `サーバー証明書`、`情報提供依頼書` → `RFI` などが該当する。

別の概念、対になる語、上位・下位の語を、リンク先を用意するためだけに別名にしない。例えば `IPS` を `IDS` の別名にはせず、`ファストトラッキング` を `クラッシング` の別名にもしない。過去問の復習単語からは、その単語自体を学べる用語へ対応させる。

## 評価観点の数・区分をそろえない

- その用語自体の理解を確かめるために必要な観点だけを設ける。基本が1個で十分なら1個にする。
- 基本は試験で押さえる意味・目的・基本の仕組みを扱う。頻出の標準的な対策や計算式も対象にできるが、細部の網羅や関連語の定義を合格条件にしない。
- 深掘りは、その用語について理解が深まる補足やtipsがある場合に設ける。理由・使いどころ・制約・影響・具体的な条件・実務の注意点を扱える。過去問にそのまま出た論点に限定せず、内容の正確さを一次資料で確かめる。別の概念の詳説を一括で要求しない。
- 基本だけの用語でもよい。区分を埋めるために周辺知識を足さない。例えば「量子コンピュータ」は量子ビットの重ね合わせを利用して計算するという基本を中心にし、量子アニーリング・量子もつれ・個別アルゴリズムの知識まで一括で要求しない。
- 全ての基本項目を正しく説明できれば合格。深掘りが未説明・誤りでも基本の合格を取り消さず、誤りは該当項目に訂正点として示す。基本にも関係する誤りは、その基本項目で評価する。
- 深掘りを1項目以上正しく説明でき、深掘り内に誤りがなければ「合格 ＋ 深掘りできた」。全ての深掘り項目を埋める必要はない。誤りがあるときは訂正を優先し、追加の達成表示は保留する。
- 基本だけの用語は合格で完了する。存在しない深掘りを不足として指摘したり、自動的に深掘り達成にしたりしない。
- `definition`は基本の項目を満たす短い説明にする。独立した「例えば」の欄は設けない。深掘り・tipsには`criteria`の深掘り項目の本文を表示し、説明と採点で同じ内容を使う。比較や注意点を載せる場合も、別の用語の詳しい説明まで要求しない。
- 採点範囲は項目の本文で決める。`hint`は理解を助ける問いであり、追加の必須条件にしない。定義や注意点に書かれた補足も、自動的に必須としない。代表例の列挙は全件を要求せず、定義に不可欠な構成要素とは区別する。
- 採点では、説明文にない主語・対象・関係を参照資料や一般知識で補完しない。意味が同じ言い換えは認めるが、概念の取り違えを音声の誤変換として正解に直さない。
- 入力方法を問わず、誤字・脱字・近い音の誤変換・助詞の誤りは、前後の語と動作から自然に読み取ってから採点する。誤字だと断定できることや解釈の完全な一意性までは要求しない。用語資料は語の表記を特定する手掛かりに使えるが、書かれていない知識を足さない。表記だけで減点せず、明確な言い直しは訂正後を評価する。公開鍵と秘密鍵の取り違えなど、自然に読んでも内容の誤りとなる主張は正答へ直さない。
- 文が「〜を悪用して」などで途切れていても、対象と動作から項目の意味が伝われば認める。各項目を独立して評価し、別項目の未説明や文全体の未完結を理由に、説明できた項目を未説明にしない。
- 音声入力を使った説明では、その事実と音声認識の書き起こしであることを採点指示に明示する。同音の漢字違いに限らず、読みの音が近い語も前後の説明から意図した用語として読めれば許容する。長音・促音・濁音や語の区切りのずれ、言いよどみ自体を減点しない。音の近さだけで正答にせず、説明された動作と関係の意味を評価する。
- 誤認識が別の普通の日本語として成立していても、文字通りの意味に固定しない。短い説明でも、対象の用語・評価項目と読みの近さを手掛かりに専門用語へ読み替えてよい。例えばROC曲線の「利用成立」は「偽陽性率」として扱える。ただし「縦軸を利用成立」なら「縦軸を偽陽性率」と復元し、縦横や真偽の対応まで正答に合わせて直さない。
- 音や文脈からの読み替えはAIへの採点指示で許容する。個別の誤認識例を、コードによる固定置換の許可と解釈しない。AIには説明の原文を送り、用語別の置換表で事前に書き換えない。
- 採点指示は「音と文脈から説明を読み取る→その意味で項目ごとに採点する」の順を短く明示する。個別の失敗への注意書きを継ぎ足すより、共通指示と少数の入出力例を整理し、同じ説明群で変更前後を比較する。

## 既存の用語を分割するとき

既存のIDは分割先の1語に引き継ぎ、残りの語には新しいIDを付ける。保存済みの説明・評価は当時の記録として残し、書き換えない。過去問の復習単語、別名の対応、`related` のリンクを確認し、分割後の各語へ個別に移動できるようにする。

データは `src/features/glossary/terms.ts`、段階の判定は `src/features/glossary/model.ts`、AIへの指示は `src/server/glossary-evaluator.ts` にある。編集時は用語データとAIへの指示の両方で、この方針と矛盾していないか確認する。
