# 誤字・脱字の評価確認

現在は個別の固定置換を行わず、説明文の原文をAIへ送り、音と文脈からの読み替えを採点指示で許容する。以下の固定置換を含む検証は撤回前の記録であり、現行処理ではない。

単体テストのモック応答では、採点指示が実際のモデルに伝わったか確認できない。誤字を含む説明と、表記だけ直した説明を実APIで比較する。

## 修正前に確認した結果（2026-10-21）

Pass the Hash攻撃で、稼働中のAPIへ各1回送信した結果。実行先は `https://orenotameno.atuya07261008-748.workers.dev`。当時は採点方針のバージョンを返していなかったため、適用されたコミットは特定できない。

| 入力 | `hash-auth` の選択 | coveredの推定確率 | 期待 |
|---|---|---|---|
| パスワードのハッシュ時だけをみて認証する仕組みは悪用して | missing | 38% | covered |
| パスワードのハッシュ値だけをみて認証する仕組みを悪用して | missing | 49% | covered |

両方とも「ハッシュ値だけで認証できる仕組みを悪用する」という論点は伝わる。「解読せず、そのまま認証に使う」はこの文では説明されていないため、そちらの項目はmissingのままにする。したがって、この入力だけで最終評価がCになること自体は変更対象ではない。

## 修正後に確認した結果（2026-10-21）

コミット `fe0938a` のCloudflare Workers Builds成功と、本番APIの `X-Glossary-Policy: 2026-10-21-typo-fragments` を確認後、6例を各1回送信。指定した項目別の最終statusは6例とも期待値に一致した。推定確率と選択には揺らぎがあるため、同じ文章が常に同じ数値・結果になる保証ではない。

| 確認例 | 対象項目の結果 | coveredの推定確率 | 最終評価 |
|---|---|---|---|
| 報告された誤字・助詞誤り・言いさしを含む文 | hash-auth: covered / no-crack: missing | hash-auth: 78% | C（no-crackが未説明） |
| 表記を直した言いさしの文 | hash-auth: covered / no-crack: missing | hash-auth: 77% | C（no-crackが未説明） |
| 解読せずそのまま使う説明を加えた、誤字ありの文 | Bの2項目ともcovered | hash-auth: 82% / no-crack: 94% | B |
| 同じ説明の表記修正済みの文 | Bの2項目ともcovered | hash-auth: 91% / no-crack: 96% | B |
| 必ず解読して平文パスワードを求めるという誤り | no-crack: review | 0%（review: 99%） | C |
| パスワードとハッシュ値に関係する攻撃、という言及だけ | 全項目missing | hash-auth: 2% / no-crack: 1% | C |

誤字ありの言いさしでno-crackをcoveredと選んだ返答（54%）や、基本を説明した誤字ありの文でlateralをcoveredと選んだ返答（56%）もあったが、70%下限によって最終statusはmissingになった。未説明の意味をモデルが補完する揺らぎは残っているため、この6例の成功だけで解消済みとは扱わない。

## 実APIによる確認

音声入力の利用情報を追加した初版 `cc7730c`（`2026-10-21-speech-context`）では、7例中6例が期待した最終statusに一致した。「ハシュち」の例はB（hash-auth: 88%、no-crack: 95%）だったが、報告された言いさしの文はhash-authのcoveredが66%で保留になった。この結果を受け、表記の復元確度と読み取った内容の理解を区別し、助詞の乱れや口頭の言いさしの扱いを明示した。

続く `33100dd`（`2026-10-21-speech-context-v2`）では、報告された文のhash-authが85%でcovered、「ハシュち」の文はB（hash-auth: 94%、no-crack: 98%）になった。一方、修正済みの完全な説明から、未説明の横展開までcovered（71%）とした返答があり、7例中6例の一致だった。このため、表記を読み替える際にも、項目が求める出来事・場所・対象を追加しないことを項目別指示に明示した。

最終調整 `ff4591e`（`2026-10-21-speech-context-v3`）の本番反映後、7例を各1回送信し、すべての指定項目が期待した最終statusに一致した。報告された文のhash-authは81%でcovered、表記修正済みの言いさしは85%でcovered。「ハシュち」の文はB（hash-auth: 96%、no-crack: 100%）。完全な説明の誤字あり・修正済みもBとなり、横展開は両方ともmissingだった。事実の誤りはreview（100%）、単なる関連語への言及は全項目missing。これは各1回の確認であり、今後の揺らぎがなくなったことまでは示さない。

[確認例](../scripts/glossary/typo-cases.json)は、上の2文、基本項目を説明した誤字あり・修正済みの2文、事実の誤り、未説明、読みの音が近い「ハシュち」、ROC曲線の「利用成立」と表記を直した文の4例の計11件。`usedVoice` で音声入力かどうかも送り、修正済みの2文は文字入力、それ以外は音声入力として確認する。ROC曲線では「利用成立→偽陽性率」の復元を認めた上で、縦軸・横軸の誤りは正答へ直さないことも比較する。項目別の最終statusを確認し、推定確率も出力する。モデルの揺らぎがあるため、1回の成功は常に同じ結果になる保証ではない。

`e6cf04c`（`2026-10-21-phonetic-words`）は指示だけで「利用成立」の復元を試したが、11例中8例の一致にとどまった。正しい軸の説明でもcoveredの推定確率が41%で保留になり、誤った軸の短い説明は原文・表記修正済みともreviewではなくmissingだった。この結果を受け、ユーザーが明示した対応をROC曲線の採点入力で先に復元する処理と、項目内に明確な誤りがある場合は未説明よりreviewを優先する指示を追加した。

明示的に実行した場合だけ11回の有料AI評価を行う。通常の `npm test` には含めず、自動再試行しない。

```sh
node scripts/glossary/check-typo-tolerance.mjs https://対象サイト 2026-10-21-phonetic-context-only
```

最初にGETで `X-Glossary-Policy` を確認し、指定した採点方針と異なる場合はAI評価を送信せず終了する。これにより、旧版のAPIを新しい指示の検証結果として扱うことを避ける。

`f3b3e59`（`2026-10-21-confirmed-speech-words`）では、ROCの正しい軸の説明は「利用成立」あり・修正済みの両方ともaxesがcovered（100%）となり、同じB評価だった。誤った軸の短い説明も両方axesがreview（97%）となり、語の復元と軸の評価は一致した。ただし軸の誤りが無関係な3項目にもreviewとして波及し、既存の表記修正済みの言いさし1例も67%で保留となったため、11例中8例の一致だった。項目間の誤りの波及を防ぐため、各項目が未説明なら他項目の誤りによらずmissingにすることを追記した。

`836ad0b`（`2026-10-21-confirmed-speech-words-v2`）でも、ROCの誤認識あり・修正済みの比較は、正しい軸・誤った軸の両方で項目別の選択・確率・最終評価が一致した。正しい軸の文はB（axesのcovered: 100%）、誤った縦軸の短い文はC（axesのreview: 92%）。語の復元は確認できたが、誤った短文からupperleft・diagonalにもreviewが波及することと、既存の文字入力の言いさしが68%で保留になることは残り、全期待値に一致したのは11例中8例。これらは解消済みとして扱わず、今回確認できた「利用成立→偽陽性率」の復元とは区別して記録する。

ユーザーの指摘を受け、個別の読み替えを許可する採点指示と、原文の固定置換を混同していたことを訂正した。`confirmedSpeechCorrections` と採点前の置換を削除し、原文がそのままAIへ渡ることを単体テストで確認する。固定置換時の結果を、現行指示だけでの検証結果としては扱わない。
